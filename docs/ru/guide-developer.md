# Руководство разработчика: DiffMosaic в работе с pull request

## 1. Что подготовить

Нужны локальная копия Python-проекта, Git и установленный DiffMosaic. Команды
ниже рассчитаны на PowerShell и Python 3.11+.

```powershell
git clone https://github.com/FlaksAngel/diffmosaic.git
cd diffmosaic
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
```

Целевой проект должен уже быть клонирован локально. `--base` и `--head` — две
существующие ревизии в нём. Например, до начала ревью ветки `feature/login`
можно сравнить её с `origin/main`.

## 2. Получить первичный отчёт

```powershell
diffmosaic analyze `
  --repo C:\work\target-project `
  --base origin/main `
  --head feature/login `
  --format markdown `
  --output diffmosaic-analysis.md
```

Отчёт содержит изменённые производственные файлы, тестовые файлы, сущности
Python (функции, методы, классы), их строки и строки diff. Это уже полезно для
ревью: вместо ручного поиска по большому diff можно начать с конкретных
функций, в которых изменилось поведение.

Важно: строка, которую нельзя привязать к функции или классу, сохраняется как
`unmapped`, а не исчезает из анализа. Так не маскируются модульные выражения,
удаления или синтаксис, который AST не может привязать к символу.

## 3. Добавить фактическое покрытие — необязательный, но сильный шаг

DiffMosaic не запускает тесты при `analyze`. Если вы доверяете целевому
репозиторию и уже запускаете его тесты обычным способом, отдельно создайте
артефакт покрытия:

```powershell
cd C:\work\target-project
coverage run -m pytest
coverage json -o coverage.json

diffmosaic analyze `
  --repo C:\work\target-project `
  --base origin/main `
  --head feature/login `
  --coverage-json C:\work\target-project\coverage.json `
  --format markdown
```

Если путь из `coverage.json` неоднозначен или не сопоставляется с файлом Git,
в отчёте будет «нет данных», а не ложное утверждение «строка не покрыта».

## 4. Сформировать объяснимую очередь ревью

```powershell
diffmosaic prioritize `
  --repo C:\work\target-project `
  --base origin/main `
  --head feature/login `
  --coverage-json C:\work\target-project\coverage.json `
  --format markdown `
  --output review-queue.md
```

Приоритет — не вероятность ошибки. Это сумма опубликованных причин: например,
изменена производственная функция, тестовые файлы не менялись, а данных о
покрытии нет или они частичны. Откройте первые 3–5 позиций и задайте автору PR
конкретный вопрос: «Какой тест фиксирует это граничное условие?».

## 5. Построить план мутаций без исполнения кода

```powershell
diffmosaic mutate-plan `
  --repo C:\work\target-project `
  --base origin/main `
  --head feature/login `
  --format markdown `
  --output mutation-plan.md
```

Планировщик ищет только два типа простых изменений и только там, где изменился
производственный Python-код:

- границы сравнений: `>`, `>=`, `<`, `<=`, `==`, `!=`;
- логические связки: `and` и `or`.

План пригоден для ручного обсуждения. Например, если изменение в коде меняет
`age > 18` на `age >= 18`, хороший тест должен различать значение ровно 18.

## 6. Выполнить мутации только в доверенной среде

Этот шаг не обязателен для ежедневного ревью. Он нужен, когда команда готова
выделить контейнер с уже установленными зависимостями и доверяет его тестовой
команде.

```powershell
diffmosaic mutate-run `
  --repo C:\work\target-project `
  --base origin/main `
  --head feature/login `
  --image company-target-tests:locked `
  --output mutation-results.json `
  --workdir /workspace `
  --allow-execution `
  --test-command python -m pytest
```

`/workspace` — значение по умолчанию и всегда доступно только для чтения.
Если проверяемый тест создаёт относительный временный файл, допустимо выбрать
`--workdir /tmp`, но путь к самому тесту в команде должен быть явным,
например `/workspace/tests/test_feature.py`. Выбранная рабочая папка попадёт в
JSON-отчёт и в замороженный исследовательский манифест.

Сначала исходная версия тестируется в тех же ограничениях. Если базовые тесты
не прошли, кандидаты не запускаются: сравнение было бы нечестным. Для каждой
мутации возможен один из результатов:

| Результат | Смысл |
| --- | --- |
| `killed` | После изменения тесты упали; набор тестов различает поведение. |
| `survived` | Тесты прошли; это повод изучить пробел в тестах, а не доказательство дефекта. |
| `timeout` | Запуск не уложился в лимит; результат не включается в адекватность. |
| `infrastructure_error` | Среда или команда дала сбой; вывод о тестах делать нельзя. |

`mutation adequacy = killed / (killed + survived)`. Тайм-ауты и ошибки среды
не добавляются ни к числителю, ни к знаменателю.

## 7. Что положить в pull request или отчёт ревью

Не публикуйте только число. Сохраните рядом с PR:

1. хеши `base` и `head`;
2. отчёт `analyze` или `prioritize`;
3. версию DiffMosaic;
4. при наличии исполнения — образ Docker с digest, точную тестовую команду и
   `mutation-results.json`;
5. короткое человеческое решение: какой тест добавлен либо почему риск
   приемлем.

Так коллега может воспроизвести не только вывод, но и основание для вывода.
