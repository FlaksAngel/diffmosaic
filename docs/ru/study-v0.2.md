# Исследование DiffMosaic v0.2

Этот документ описывает следующий научный этап проекта. Его цель — не
«доказать, что инструмент находит ошибки», а проверить, помогает ли его
фиксированная очередь ревью выделять изменённые символы с более слабым
мутационным подтверждением, чем простое правило «в PR не менялись тесты».

Полная техническая спецификация находится в
[английском протоколе](../study-v0.2-protocol.md). Здесь — рабочая схема.

Текущее состояние — `preliminary`: закреплены 7 статически отобранных записей
из 4 публичных проектов и их SHA-256 screen-отчёты. Для двух attrs-записей
уже сохранены все пять study-артефактов и результаты мутаций; одна Requests-
запись сохранена как исключение из-за политики `network=none`; HTTPX остаётся
инженерной квалификацией. Корпус ещё не заморожен и не имеет агрегированного
вывода, поэтому это не результат исследования в целом.

## Что считается одной записью

Одна запись — фиксированная пара Git-коммитов в публичном Python-проекте. Внутри
неё оценивается не весь PR целиком, а конкретная изменённая функция, метод или
класс, для которого DiffMosaic смог построить хотя бы одну мутацию.

Для каждого символа сохраняются:

- его score и причины приоритета;
- данные coverage;
- число запланированных мутаций;
- `killed`, `survived` и неконклюзивные результаты;
- `mutation_adequacy`;
- отметка, слабое ли это тестовое подтверждение по заранее заданному порогу.

## До начала сбора результатов

1. В [`corpus/study-v0.2.json`](../../corpus/study-v0.2.json) заранее заданы
   порог `0.8`, минимум один конклюзивный мутант и набор операторов `v0.2`.
2. Выбирается правило отбора коммитов: например, фиксированный период и первые
   подходящие non-merge изменения в истории каждого проекта.
3. В манифест вносятся и удачные кандидаты, и исключения. Нельзя заменять
   неудобный результат другим коммитом после запуска.
4. Цель feasibility-этапа — 6 study-записей из 3 независимых сообществ;
   цель полноценного эмпирического исследования — 18–24 записи из 4+ сообществ.

Для фиксированного и проверяемого отбора используй read-only команду:

```powershell
diffmosaic screen --repo C:\work\target --repository-label https://github.com/example/project `
  --max-commits 120 --operator-set v0.2 `
  --output screening.json
```

Она просматривает non-merge историю от новых коммитов к старым и сохраняет
каждый просмотренный коммит, наличие изменённых тестов и число найденных
мутаций. Eligible становится только коммит с мутацией, привязанной к изменённой
именованной Python-сущности. Она не выполняет исходный код и не видит исходов
мутаций.

В каждой `candidate` и `study` записи манифеста сохраняются путь, SHA-256 и
ordinal экранного отчёта. Валидатор сверяет URL проекта, версию планировщика,
набор операторов и точную пару base/head; нельзя вручную выдать произвольный
коммит за прошедший статический отбор.

## Какие файлы обязательны для study-записи

Для каждого subject создаются JSON-файлы `analysis`, `priority`, `coverage`,
`mutation_plan` и `mutation_results`. В манифест записываются их пути
относительно корня репозитория и SHA-256. Там же фиксируются коммиты, digest
Docker-образа, тестовая команда, рабочая папка контейнера, лимиты и версия
операторов. Разрешены только `/workspace` (read-only, по умолчанию) и `/tmp`
(ограниченная временная файловая система); выбор также сверяется валидатором.

```powershell
diffmosaic corpus-validate --manifest corpus\study-v0.2.json --verify-artifacts --format markdown
```

Эта команда только читает локальные файлы: не загружает репозитории, не строит
образы и не запускает тесты.

## Как получить итоговую таблицу

Когда манифест получает статус `frozen`, запускается:

```powershell
diffmosaic evaluate --manifest corpus\study-v0.2.json --format markdown --output study-results.md
```

Она объединяет артефакты автоматически. Если SHA-256, base/head, набор
операторов, Docker-образ, команда, рабочая папка, лимиты или список мутантов не совпали,
команда завершится ошибкой вместо подготовки таблицы. При равных score average
precision считается с учётом всех возможных порядков внутри ничьей: случайный
порядок идентификаторов не даёт преимуществ ни инструменту, ни baseline.

## Эквивалентные мутанты

Выживший мутант — повод разобраться, а не автоматическое доказательство
плохого теста. Его можно исключить только вручную как `equivalent` или
`duplicate`, указав id кандидата и конкретную причину. Инструмент разрешит это
только для реально выжившего кандидата из сохранённого плана; убитый мутант или
ошибку среды скрыть нельзя.

## Повторный запуск

Для замороженной записи доступны только параметры, зафиксированные в манифесте:

```powershell
diffmosaic reproduce --manifest corpus\study-v0.2.json --subject <subject-id> `
  --repo C:\work\target --output reproduced-results.json --allow-execution
```

Команда откажется выполнять тесты, если локальный Docker-образ не совпадает по
digest с зафиксированным или текущая версия планировщика построит другой набор
идентификаторов мутантов. Несмотря на ограничения контейнера, запускай только
код и образы, которым можно доверять.
